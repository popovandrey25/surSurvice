# surService

Backend конструктора многостраничных опросов на Django 5.2 LTS и Django REST Framework.
Есть JWT-авторизация, CRUD опросов, публикация, приём ответов, статистика и экспорт JSON/XLSX.
Фронтенд пока отсутствует; API можно исследовать в браузере через DRF Browsable API.

## Локальный запуск

Python 3.13 или 3.14. Команды выполняются из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python surService/manage.py migrate
python surService/manage.py createsuperuser
python surService/manage.py runserver
```

В Windows PowerShell активация: `.venv\Scripts\Activate.ps1`.
Админка: http://127.0.0.1:8000/admin/, API: http://127.0.0.1:8000/api/v1/.
SQLite создаётся при `migrate`. Существующую базу перед обновлением зависимостей следует скопировать.
Данные приложения сохраняются: его модели и исторические миграции не переименованы.
Обновлённый Simple JWT применит собственные дополнительные миграции.

Настройки читаются из переменных окружения. Локально работают значения по умолчанию:
`DJANGO_DEBUG=true`, localhost в `DJANGO_ALLOWED_HOSTS`, CORS для localhost:5173.
Образец настроек — `.env.example`. Файл `.env` автоматически не загружается; в Bash:

```bash
cp .env.example .env
set -a
source .env
set +a
```

Для развёртывания нужны отдельный секрет `DJANGO_SECRET_KEY`, `DJANGO_DEBUG=false`
и явные хосты/источники CORS. При выключенном DEBUG запуск без секрета запрещён.
Встроенный ключ предназначен только для локальной разработки. Старые JWT после смены ключа не действуют.

## Устройство кода

- `surService/surService/urls.py` — подключение админки и API приложения.
- `surService/surApp/urls.py` — router автора и маршруты участника.
- `views.py` — `VotingViewSet` для автора и отдельные views участника.
- `auth_urls.py`, `auth_views.py` — регистрация и JWT.
- `serializers.py` — проверка входных данных и представления ответов.
- `permissions.py` — проверка авторства; queryset автора также ограничен его опросами.
- `services.py` — транзакции сохранения дерева опроса, публикации и приёма ответов.
- `tests.py` — API-тесты доступа, авторизации, целостности данных и экспорта.

Модели: `Voting → Page → Question → Choice`, выбранные варианты — `Vote`.
Неиспользуемая старая модель `Survey` сохранена ради совместимости с существующей базой.

## Контракт API v1

Префикс всех маршрутов: `/api/v1/`. Старые URL (`create/voting/`, `api/answer-voting/` и другие)
заменены, обратных алиасов нет. Списки автора и его ответы имеют пагинацию по 20 записей:
`{count, next, previous, results}`; следующая страница задаётся через `?page=2`.

### Авторизация

| Метод | Путь | Тело / результат |
| --- | --- | --- |
| POST | `auth/register/` | `{username, email, password}`; пароль проходит Django-валидацию |
| POST | `auth/login/` | `{username, password}` → `{access, refresh, user_id}` |
| POST | `auth/token/refresh/` | `{refresh}` → `{access}` |
| GET | `auth/token/validate/` | Проверка текущей авторизации |
| POST | `auth/logout/` | `{refresh}`; требуется авторизация того же пользователя; ответ 204 |

Для защищённых запросов: `Authorization: Bearer <access>`.
Access действует 15 минут, refresh — сутки. Выход блокирует refresh; уже выданный access
остаётся действительным до истечения срока. Также включена session-аутентификация
для Browsable API: можно войти в админку и открыть API в том же браузере.

### Управление опросами — только автор

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET / POST | `votings/` | Список своих опросов / создание черновика |
| GET / PUT / PATCH / DELETE | `votings/{id}/` | Получение / полное и частичное обновление / удаление |
| POST | `votings/{id}/publish/` | Публикация |
| POST | `votings/{id}/unpublish/` | Закрыть доступ участникам |
| GET | `votings/{id}/statistics/` | Число голосов по вариантам |
| GET | `votings/{id}/responses/` | Ответы с ID участников, вопросов и вариантов |
| GET | `votings/{id}/export-json/` | Структура опроса в JSON |
| GET | `votings/{id}/export-votes/` | Ответы в XLSX |

Чужой опрос возвращает 404. `author` определяется по авторизации, `is_submit` меняется
только действиями публикации. DELETE намеренно удаляет опрос вместе с ответами.

Пример тела `POST /api/v1/votings/`:

```json
{
  "title": "Обратная связь",
  "description": "Расскажи о впечатлениях",
  "pages": [
    {
      "title": "Общие вопросы",
      "order": 0,
      "questions": [
        {
          "title": "Что понравилось?",
          "type": "checkbox",
          "choices": [{"name": "Интерфейс"}, {"name": "Скорость"}]
        }
      ]
    }
  ]
}
```

Правила редактирования:

- `PATCH {"title": "Новое название"}` сохраняет все страницы, вопросы и ответы.
- Если передано `pages`, это полное желаемое дерево: страницы содержат `questions`,
  вопросы — `choices`; обязательные поля элементов должны быть заполнены даже при PATCH.
- Существующие элементы передаются со своими `id`, новые — без `id`.
  ID должны принадлежать соответствующему родителю; отсутствующие в списках элементы удаляются.
- Структуру и правила переходов можно менять только в черновике без ответов.
  Название и описание можно менять после публикации и получения ответов.
- Пустой черновик разрешён, но публикация требует страниц с вопросами и вариантов ответа.
- `checkbox` разрешает несколько вариантов, `radio` — один. Остальные типы пока не поддерживаются.

Правила скрытия страниц пока сохраняют прежний формат JSON-строк:
`question_answer_pairs`: `"[[question_id, choice_id]]"`, `hidden_pages`: `"[[page_id]]"`.
Массивы должны иметь одинаковую длину; все ссылки проверяются на принадлежность опросу.
Если дерево меняется, нужно сохранить используемые ID либо обновить/очистить правила в том же запросе.

### Участник

- `GET public/votings/{id}/` — опубликованный опрос, доступен без входа.
- `POST public/votings/{id}/submissions/` — отправка выбранных вариантов, требуется вход.

```json
{
  "answers": [
    {"question": 1, "choice": 2},
    {"question": 1, "choice": 3}
  ]
}
```

`user` в элементах запрещён: сервер использует текущего пользователя. Пустой пакет,
дубликаты, чужие вопросы/варианты и несколько вариантов для `radio` возвращают 400.
Сохранение атомарно: либо весь пакет, либо ничего. Успех — 201 и список сохранённых `Vote`.
Один пользователь может отправить один пакет на опрос; повторная отправка запрещена.
Заполнять все вопросы не обязательно: обязательность и вычисление ветвлений на сервере пока не реализованы.

## Проверки

```bash
python surService/manage.py check
python surService/manage.py makemigrations --check --dry-run
python surService/manage.py test surApp
```

Тесты создают отдельную временную базу. GitHub Actions выполняет эти команды на Python 3.13 и 3.14.
Зависимости верхнего уровня находятся в `requirements.in`, зафиксированные версии — в UTF-8 `requirements.txt`.
Обновление с установленным `uv`:

```bash
uv pip compile requirements.in --python-version 3.13 --universal --output-file requirements.txt
python -m pip install -r requirements.txt
```

## Границы текущего этапа

Отдельной модели прохождения `Submission` ещё нет: endpoint сохраняет пакет существующих `Vote`.
Повторная отправка и изменение структуры проверяются в сервисах под транзакцией.
SQLite использует `IMMEDIATE`, сериализуя записи; для базы с блокировками строк сервисы используют
`select_for_update()` на опросе. Это не нагрузочное тестирование и не защита от прямых записей в ORM
в обход сервисов. Админка остаётся инструментом доверенного администратора.

Следующие самостоятельные этапы: модель прохождения и ограничения БД, OpenAPI-схема,
демоданные, фронтенд и конфигурация развёртывания с PostgreSQL.
